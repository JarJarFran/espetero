# Espetero 0.1.2 against the other engines: MacBook Pro M1 Max

MacBook Pro with an M1 Max (64 GB), measured on 2026-10-26 and 2026-10-27.
The protocol is the one in [README.md](README.md#method): the same client,
[tools/bench_compare.py](../../tools/bench_compare.py), greedy decoding with
thinking off, 16 parallel slots and a 40K context in every server, and the
median over each cell's requests. Every run had the GPU to itself (an
exclusive gputurn job; runs another app shared the GPU with were measured
again and left out). Every request is in
[2026-10-27-m1-max.jsonl](2026-10-27-m1-max.jsonl).

Engines: Espetero 0.1.2 (6c0c657; Qwen3.8-Flash-Next with 4483e19, see below),
llama.cpp b11429, mlx-lm 0.32.2 (mlx 0.32.4). Server flags as in the README.

Changes from the October 11 runs:

- **Fewer competitor workloads.** The other engines ran decode, code, prefill,
  8 and 16 users and the image: no 4 users, no decode after a long context,
  no 32K prompt, no answer checks. Espetero ran the full set. Empty
  cells (–) in the other engines' columns are workloads they did not run, not
  failures.
- **No oMLX, vLLM-metal or BaseRT on this Mac** this time.
- **Load time** is not comparable with the October tables: the model files
  were read over the network from the Mac Studio's disk (Flash-Next's from
  the SSD).
- **Qwen3.8-Flash-Next** does not fit in 64 GB: Espetero keeps the experts on
  the SSD and caches the ones in use (31–32 GB of cache with 4483e19). Earlier
  builds sized that cache to leave less memory free, and the system's memory
  guard stopped the server during the 8K and 32K prompts; 4483e19 leaves 18 GB
  free and ran every workload. The SSD reads bound the multi-user rows: on a 64 GB
  Mac, Flash-Next is a model for one or a few users.
