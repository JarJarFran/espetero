# Changelog

## 0.1.2 (in preparation)

- **Macs with 128 GB (M4 Max)**: Qwen3.8-Flash-Next (`qwen4_exp`) keeps every expert resident when the whole store fits and routes on the GPU with no per-layer handshake (`ESPETERO_RESIDENT=0` keeps the expert cache); a fused parallel route for 257-512 experts and hyper-connection fusions. The fusions are bit-identical; the parallel route sums each expert's partial logits in another order, so 1-row decode, verify and split rows differ in the last bits from the expert-cache path (M4 Max verification, 3 cases: no expert, argmax or greedy token changed; `ESPETERO_ROUTE_PAR=0` restores the bit-identical route). M4 Max 128 GB, Flash-Next oQ4e: 26.5 -> 16.5 ms per decode step against 0.1.1 (33.4 -> 60.2 tok/s).
- **Flash-Next on 128 GB (Fase 3)**: the resident experts (77 GB) live in memory locked with `mlock`: the first pass after loading took 10 s of wall time for 0.2 s of GPU time (macOS compressed the idle GPU's memory, private or shared, once the load had filled free memory; the pass decompressed it), now 0.4 s, 2.1 s after 90 s of idle (`ESPETERO_XRES_MEM`). The oQ4e file's own 4-bit MTP head drafts when no drafter directory is beside the model (`--mtp own` forces it), and Flash-Next's drafts now score the coarse 2-bit LM head with the exact head over the shortlisted blocks (`--mtp-coarse`, as the Qwen3.5 models; a draft step 1.9 → 1.0 ms): on the M4 Max the own head accepts drafts like the bf16 drafter (44–67 % on three prompts) and decodes at 72–97 tokens/s against 59 plain, with identical replies. `ESPETERO_WEIGHTS_LOCK=1` (opt-in) also locks the weights: the first pass after an idle 2.1 → 1.2 s. `ESPETERO_XPIPE` cannot matter there: the long-pass pipeline runs only when a layer routes more experts than its pool has slots, and a 128 GB Mac's pool holds all 512. Measurements in [docs/qwen4_exp.md](docs/qwen4_exp.md) §7 and §9.
- **DeepSeek-V4.1 decode anatomy (Fase 3)**: on the M4 Max a decoded token is 82 ms = GPU 40 + command-buffer launch and wake-up 5.6 + expert reads 34 (12 misses) + Engram rows 1 + host 0.9 ([docs/deepseek_v41.md](docs/deepseek_v41.md) §5, with the per-kernel split and the cache-size replay). The Engram rows are now gathered while the GPU runs the first layers (`ESPETERO_DS4_ENGRAM_BG=0`). Two bit-identical restructurings measured slower and stay opt-in: one hyper-connection dispatch between sub-layers (`ESPETERO_DS4_HCFUSE=1`: GPU 40.1 → 44.2 ms per token) and the pass as one command buffer with the host signalling each layer's experts (`ESPETERO_DS4_DRIVE=1`: +16–28 ms per token; a GPU wait on a host-signalled event costs far more than a command buffer launch). `build/dsv4_run` prints logits hashes with `DS4_RUN_HASH=1`.
- **DeepSeek-V4.1** (`deepseek_v41`, experimental): DeepSeek-V4.1-Flash (552B, 16B active) on a 128 GB Mac with the routed experts and Engram tables read from the SSD (≈ 11 GB in memory, an automatic expert cache that leaves ~14 GB to the Mac): DSML tool calls, images (DeepSeek ViT), slot checkpoints on disk, decisions (leaves); about 10 tokens per second of decode on an M4 Max. Architecture, parity and measurements: [docs/deepseek_v41.md](docs/deepseek_v41.md).
- **Qwen3.8-Flash-Next from GGUF** (`qwen4exp`, work in progress): experts whose shared and routed widths differ per matrix (for example Q4_K gate/up beside a Q5_1 or Q8_0 down) take the 8-bit shared-expert kernels per matrix.
- **Gemma 4 vision**: chat requests with images on Gemma 4 26B-A4B and 31B, from MLX directories and from llama.cpp GGUF with a `gemma4v` mmproj. The processor follows transformers' Gemma4 processor (70 to 1120 soft tokens by image budget; 280 at the standard budget); image tokens attend to their whole image in the sliding-window layers, as transformers and vLLM build the mask; the images of a pass give the same soft tokens as each one alone. `tools/gemma4_lora_convert.py` merges a decision LoRA (for example `autotrust/GEV-26B-Decide`) into an 8-bit MLX directory.
- **Gemma 4 unified (12B)**: `gemma4_unified` with its encoder-free vision embedder (one soft token per 48x48-pixel block), from MLX directories and BF16 GGUF + mmproj (`tools/gemma4_unified_convert.py` converts both). Decision heads over the last hidden state (`"head": {"slots": n}` on chat completions and completions; `akhilaaa3/Jev-Omni`) and a raw prompt mode with per-part checkpoints (`chat_template_kwargs.raw_prompt`; `EldanRing/Winnow-12B`'s letter labels through the score read-out).
- **Noncausal decision heads**: `perplexity-ai/pplx-decider-v1.1-27b` (Qwen3.8-27B, images and text; a readout over the last hidden state, trained without the causal mask in its full-attention layers) converts with `tools/pplx_decider_convert.py` and answers chat requests with `"head"`: the prompt runs in one pass with bidirectional full attention (DeltaNet layers unchanged), nothing cached, the probabilities at the release's calibration temperature (`head.temperature`); `/v1/systemone` renders the release's decisions (`noul`, `choice`, `score`, with images) and answers with its typed answers; its other requests get a 422 (no LM head).
- **Kev decision models**: `jaredpalmer/kev-27b` (Qwen3.8-27B with every weight fine-tuned and a pointer head) converts with `tools/kev_convert.py` (8-bit decoder; the head read from `head.pt` without unpickling it) and answers `/v1/systemone` as the release's server does: the state once (cached), each question as its own row continuing it, the head on the final-normed states of each option's closing token and the question's last (`TreeSpec::out_rows`, fp32 from the residual stream), probabilities at the release's temperature. `--vision-from` grafts the base model's vision tower so requests may carry images (an experiment: Kev was trained on text only).
- **Qwen3-Omni thinker**: `qwen3_omni_moe` (Qwen3-Omni-30B-A3B's thinker with its DeepStack vision tower) on the Clef path: `Cloudflare/clef-omni` converts with `tools/clef_convert.py` and answers `/v1/systemone` and `/v1/decisions` with images and text; audio and video get a 422.
- **LFM2 / LFM2-VL** (LiquidAI LFM2.5-VL-1.6B and -3B, from the Hugging Face release or an MLX conversion with `tools/lfm2_convert.py`, bf16 or 8/4-bit): gated short-convolution layers whose window is slot state, GQA attention with 64-dim heads on the paged pool, the SigLIP2 NaFlex tower and projector, and the release's image processor (512-pixel tiles and a thumbnail, Pillow-exact resizes); chat with images, structured output, embeddings, prompt checkpoints. Greedy replies equal an fp32 transformers-semantics reference on text and image prompts; the tokenizer is token for token equal to `tokenizers`.
- **d1 decision models** (`LiquidAI/d1-3B`): `/v1/systemone` and `/v1/decisions` answered from the option tokens' logits at each question's answer slot, with the release's prompt (token-identical) and answer format; several questions over one state share it as the root of one tree.
- **Performance (Fase 1)**: the tuned GEMM tiles also apply to prefill chunks above the tuned row range (`tune_clamp`; a 2048-row prefill of Qwen3.8-27B 4-bit on an M1 Max 5.9 % faster, 131 -> 139 tok/s in the paired A/B, logits bit-identical); the shared-expert gate can be folded into the router GEMM for passes of more than 8 rows (`ESPETERO_ROUTE_SG=1`, off by default: -6.9 % per 16-row step on Qwen3.6-35B-A3B, but the summation order shifts near-tied expert choices, so greedy replies can differ); Qwen3.8-Flash-Next's long-pass expert pipeline waits for its staging reads on a condition variable instead of spinning, and `commit_wait` always blocks; the library's `LoadOptions` draft defaults are the server's (the coarse 2-bit MTP head with 256 blocks rescored), so `bench_native`, `ab_native`, `parity_test` and `logits_dump` measure what `espetero serve` serves. What each experiment measured, kept or not: [docs/kernel-guidelines.md](docs/kernel-guidelines.md).

## 0.1.1 (2026-10-12)

- Automatic slots grow to `--users` (concurrent requests) when the memory budget allows, beside the KV of two full contexts. Gemma 4 31B, whose slots carry the sliding-window rings (0.84 GB each), had 8 slots: with 16 requests at once the second 8 waited for the first 8 (now 16 slots: first token about 10x sooner, 40 % more tokens per second in total). With the default 64 users, Qwen3.8-27B goes from 48 to 64 slots and from 218K to 157K tokens of KV.
- Coding agents: [docs/configuration.md](docs/configuration.md#coding-agents) shows Claude Code, Codex CLI and opencode against Espetero (each fixed a small Python package with failing tests on Qwen3.6-35B-A3B 6-bit); Codex CLI needs `web_search = "disabled"` and `[features] multi_agent = false`.
- A Responses request with tools that are not functions gets a 422 that names them, and for Codex's hosted web search and sub-agent tools the config fix.

## 0.1.0 (2026-10-11)

The first public release.

- **Models**: the Qwen3.5 family (Qwen3.5, Qwen3.6, Qwen3.8 and their finetunes), dense and mixture-of-experts, with vision and MTP heads, from MLX safetensors or GGUF (also mixture-of-experts files whose quantization differs by layer, as unsloth's UD files do), local or by Hugging Face repo id; Qwen3.8-Flash-Next with its experts streamed from the SSD. Other model types are refused at start with a message naming their type.
- **Gemma 4**: the 31B dense and 26B-A4B mixture-of-experts models from MLX safetensors (checked on 4- and 6-bit files) and llama.cpp `gemma4` GGUF (checked on UD-Q4_K_M), text only: sliding-window layers with a ring of KV blocks per sequence slot, global layers with K = V and proportional RoPE in the paged pool, GeGLU, the router with per-expert scales beside the dense MLP, soft-capped logits; its SentencePiece-style tokenizer (byte fallback, token for token equal to `tokenizers`, from `tokenizer.json` or the GGUF vocabulary), the thinking channel as `reasoning_content`, its `<|tool_call>` calls as OpenAI `tool_calls`, structured output, embeddings, prompt checkpoints and prompt-lookup drafts; raw completions and embeddings start with `<bos>`, as llama.cpp's do. Greedy replies equal mlx-lm's (fp32 reference) and llama.cpp's on the same files.
- **Model handling**: repo ids download natively (no Python) into the Hugging Face cache, in huggingface_hub's own layout, so `hf`, transformers, mlx-lm and Espetero share one copy (resumable, checksummed); a model that cannot fit this Mac is refused before its download or load, with smaller files of the same model suggested; `espetero recommend` lists the models that fit this Mac (8-bit first), and `espetero pull`, `list` and `rm` manage the models in the cache and in `~/models`.
- **APIs**: OpenAI chat completions and completions (streaming, `n` choices from one prefill, logprobs of greedy, sampled and streamed replies, tools with `tool_choice` `required` or a named function, images as data URLs and, with `--image-urls`, by URL), structured output (`response_format` `json_object` and `json_schema`, Responses `text.format`, Anthropic `output_config.format`, Ollama `format`: the reply is constrained by a grammar compiled from the schema), Responses, embeddings of the loaded model, Files and Batches; Anthropic Messages (Claude Code works against it); Ollama's API (chat, generate, embeddings, model listing; replies equal the chat route's); `/v1/decisions`; tokenize and detokenize; Prometheus metrics.
- **Engine**: one GPU pass per step for all the work in flight, paged KV cache with shared prefixes, prompt checkpoints in memory and on disk, speculative decoding with the model's MTP head and prompt lookup (verified: replies do not change), reproducible seeded sampling, budgets sized from the Mac; weights read with parallel preads (a 28 GB MoE loads in ~12 s instead of 34-49 s); decode attention reads the KV cache at ~350 GB/s at long contexts (a decode step at 32K context: Qwen3.8-27B 105 -> 77 ms, Qwen3.6-35B-A3B 22 -> 14 ms, Gemma 4 31B 173 -> 85 ms); in the general preset a new request waits at most 200 ms for running replies before its prompt runs beside them (first token 1.1 s instead of 3.6 s on the 27B while another reply streams).
- **Robustness**: a request starts once the KV cache can hold its prompt and its `max_tokens` (counted up to 8K tokens or a quarter of the cache) beside the running ones, and cached checkpoints are evicted for it only when that lets it start; if the cache still runs out, a pass skips its prompts' optional checkpoints, then prompt chunks wait, then the newest requests stop with an error that says what would fit and the others finish (a request alone fills the cache to its last block). Images and decisions too large for one pass get a 422 naming `--max-rows`; a decision that fits one waits at most 4 passes beside decoding requests. Streams that fail end with an error event and `[DONE]`. Ctrl-C ends running requests after the current pass.
- **Server**: the port opens before the model loads (a port in use fails at once; requests get 503 `{"status": "loading"}` until the model is ready); a built-in web chat at `/` (one embedded page, no other origin, a strict Content-Security-Policy); a default configuration file (`~/.config/espetero/config.json`); `espetero service install|status|logs|uninstall` (a LaunchAgent: at login, restarted if it fails) and `brew services`.
- **Security**: localhost by default; bounded request, image, upload and batch sizes; requests from web pages refused without an API key; image URLs off by default and never fetched from this machine or its networks unless `--image-urls-private`.

Known limitations:

- One trusted user: every API key holder shares the prompt cache and the Batch API.
- Not supported yet (422, never ignored): `logit_bias`, images by file id or inside tool results, built-in or server tools; in a strict JSON schema, the keywords the grammar cannot enforce (`pattern`, `format`, `multipleOf`, `uniqueItems`, ...; non-strict schemas report them instead). Forced tool calls need a chat template with Qwen's `<tool_call><function=...>` format.
- Gemma 4 runs text only: images get a 422, forced tool calls (`tool_choice` `required` or a named function) get a 422, and the E2B/E4B models (per-layer embeddings, KV-shared layers) are refused at load.
- Embeddings are the chat model's own hidden states; dedicated embedding models (Qwen3-Embedding) are not supported yet, and Qwen3.8-Flash-Next cannot serve them.
- Answers longer than 8K tokens (or a quarter of the KV cache) are not reserved in full: when many such answers run at once and the cache fills, the newest stop with a "KV cache full" error. Raise `--memory-gb` or `--kv-gb` for those workloads.
- With `--image-urls`, a host name that resolves to a public address for the check and to a private one for the connection (DNS rebinding) still receives one GET; its answer is discarded.
- On mixture-of-experts models (Qwen3.6-35B-A3B, Gemma 4 26B-A4B) a request that shares a pass with others or starts from a prompt checkpoint can pick another expert at a near-tied token, so its greedy reply can differ from there from the same request alone (dense models: log-probabilities within 0.02 nats). Drafts left replies unchanged in every test.
- One model per server: there is no loading of other models on demand.
- Tuned and tested on an M1 Max (64 GB) with macOS 26. The binary targets macOS 15 or later, but has not run on macOS 15 yet. The first start of a newly installed binary compiles the GPU kernels (5-6 s); later starts reuse them.
